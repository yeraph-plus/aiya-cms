# ADR-0010: 评论单表 + 多态关联（物理分表仅为上限）

- 状态: accepted
- 日期: 2026-08-02
- 决策者: 项目所有者 + AI 协作
- 关联: [modules/comment.md](../modules/comment.md)、ADR-0032

> ADR-0032 仅调整 comment 基实现的层级归属；本 ADR 的单表、多态关联和两趟组树决策继续有效。

## 背景

评论系统目标形态是"万物皆动态"：评论不锁定文章为主体，内容或评论回复都是一条独立评论。所有者要求：不引入动态表 + 树形自引用结构（指 WP 式或动态建表方案）；系统只承担轻社区形态，至多提供转推/引用机制；物理分表至多按内容类型以一致表结构进行。

## 决策

1. **单表 `comments`**：`target_type + target_id` 多态关联（可挂任何内容类型或评论自身）；`parent_id` + `root_id` 表达树（root_id 冗余以两趟查询组装整树，避免递归 CTE 成为常态路径）。
2. **每 target_type 的 `data` JSONB 由注册的 Pydantic Model 约束**（如审核标记）；泛型 `CommentService[TData]` 提供树构建、排序、防刷（Cache 限频）、深度上限。
3. **物理分表仅为上限而非本期实现**：当某内容类型评论量证实成为瓶颈时，允许按内容类型以**一致表结构**拆分（表名加类型后缀），拆分由 Repository 层的分表路由承担，Service 无感。本期不实现路由，仅在 Repository 设计中预留类型参数。
4. 转推/引用机制（如需）用 `data` 中注册的引用 Model 表达，不新增关联表（本期不实现）。

## 备选方案

| 方案 | 优点 | 缺点 | 未采纳原因 |
|---|---|---|---|
| 每种内容一张评论表（开局即分表） | 隔离彻底 | 表数量随类型膨胀；跨类型统计/审核流复杂 | 轻社区量级不需要，预留为上限即可 |
| 递归 CTE 实时组树 | 无冗余列 | 深树性能差；每页都 CTE 代价高 | root_id 两趟组装更简单可控 |
| 闭包表 / 物化路径 | 树查询强 | 写入复杂、对轻社区过重 | 明确"轻社区形态" |
| 邻接表仅 parent_id | 最简单 | 组树需 N 次查询 | root_id 冗余成本极低、收益明确 |

## 后果

### 正面
- 一张表服务全部评论场景，审核流、统计、迁移都只有一处。
- root_id 两趟组装：第一趟取根分页，第二趟 `root_id IN (...)` 取子树，Python 内组装——查询次数恒定（2 次/页）。

### 负面 / 代价
- root_id 是冗余写（创建时计算），需测试保证一致性。
- 多态关联失去 DB 级外键（target_id 无 FK），完整性靠 Service 校验 + 定期 Cron 清孤儿。

### 逃生门
- 分表上限触发时：Repository 层实现按 target_type 路由，Service/接口不变；历史数据可在线迁移（同构表）。
