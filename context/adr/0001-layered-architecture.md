# ADR-0001: 内核/模块/api 三层架构与依赖红线

- 状态: accepted
- 日期: 2026-08-02
- 决策者: 项目所有者 + AI 协作
- 关联: [architecture/00-overview.md](../architecture/00-overview.md)、[architecture/01-dependency-rules.md](../architecture/01-dependency-rules.md)、ADR-0032

> ADR-0032 在不改变三层依赖红线的前提下，将 Content/Taxonomy/Comment 通用基实现重新归入 kernel，并把具体内容类型声明留在 modules。

## 背景

目标系统是一套支撑下载站、图库、博客、轻社区等多种形态的通用无头 CMS 底座。各站点底层能力高度重合（用户/认证/权限/内容/评论/任务/缓存/邮件），但业务组合方式不同。需要一个长期迭代中"基础稳定、业务可插拔"的结构。系统实际只有一个维护者，不需要 Hooks 式插件生态的全面支持。

## 决策

采用三层架构，并固化为依赖红线：

1. **kernel**：核心逻辑（Identity/User/Organization 占位/RBAC/Audit/Setting/Event/Pipeline/BaseTask）+ 基础设施封装（PG、APScheduler、SMTP、Redis、日志）。初版完成后封装暴露、轻易不变动。
2. **modules**：业务模块，独立表结构、独立 Service，模块内允许调用 kernel 公开 API，模块之间禁止互相 import。
3. **api**：组合根，可自由导入所有层，负责 HTTP 适配、wiring 装配、读聚合、复合响应 DTO。

红线由架构守护 pytest 强制执行，不靠评审自觉。

## 备选方案

| 方案 | 优点 | 缺点 | 未采纳原因 |
|---|---|---|---|
| 独立微服务拆分 | 隔离彻底、可独立部署 | 运维成本高，单人维护不可行；过早分布式 | 明确吸取微服务结构优点但不独立部署 |
| 单体内插件 Hooks（WP 式 action/filter 字符串挂钩） | 灵活性最大 | 字符串约定无类型检查、调用关系隐式、调试困难 | 单人维护场景不需要；用显式 Pipeline 注册表替代（ADR-0006） |
| 扁平结构（按需分包） | 最简单 | 基础与业务混杂，长期必腐化 | 与"通用底座长期迭代"目标冲突 |

## 后果

### 正面
- 内核封装后可被未来所有站点形态复用；模块可整体替换（如评论模块重写不影响内核）。
- 依赖红线可机械执行，新人/AI 协作者无法轻易破坏结构。

### 负面 / 代价
- 模块间"借用"数据必须绕行（注入点/事件/api 聚合），简单需求偶尔显得绕。
- kernel 设计压力前置：初版必须想得足够通用。

### 逃生门
- 某模块确需直接读另一模块的表：提 ADR 并在双方文档登记，作为受控例外存在（不拆除红线，只开登记口）。
